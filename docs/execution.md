# اجرای پویا و تشخیص خطا

ماژول **نفر دوم** در مسیر [execution](../src/security_patch_validator/execution) قرار دارد. این راهنما بند ۳.۲ صورت پروژه و رابط ورودی ماژول تحلیل وصله را پوشش می‌دهد.

## اجرای مستقل

پیش‌نیازها Linux x86_64، پایتون ۳٫۱۰ به بالا، GCC/G++ و GNU binutils هستند. فرمان‌ها را از ریشهٔ مخزن اجرا کنید.

~~~bash
PYTHONPATH=src python3 -m security_patch_validator.cli execute \
  --config examples/execution/config.json \
  --output reports/local/execution.json --pretty

PYTHONPATH=src python3 -m unittest discover -s tests/integration -v
~~~

برای اجرای ایزوله روی سیستم دارای Docker، ابتدا تصویر ابزار را بسازید. ساخت تصویر به مخازن بسته‌های Debian دسترسی می‌خواهد. اجرای آزمایش شبکه ندارد و در آن مخزن فقط خواندنی است. خروجی JSON از stdout کانتینر ذخیره می‌شود.

~~~bash
docker build -f examples/execution/Dockerfile -t spv-execution .
mkdir -p reports/local
docker run --rm --network none --read-only --cap-drop ALL \
  --security-opt no-new-privileges --pids-limit 128 --cpus 1 --memory 768m \
  --ulimit core=0:0 --tmpfs /tmp:rw,exec,size=384m,mode=1777 \
  --user "$(id -u):$(id -g)" --volume "$PWD:/project:ro" \
  --workdir /project --env PYTHONPATH=src spv-execution \
  python3 -m security_patch_validator.cli execute \
  --config examples/execution/config.json --pretty > reports/local/execution.json
~~~

برای بررسی ELF یا بازبینی فایل‌های اجرا روی میزبان، از `--artifacts-dir artifacts/tmp/execution` در اجرای محلی استفاده کنید. هر اجرا زیرپوشهٔ یکتای خودش را می‌سازد. بدون این گزینه، مسیرها در گزارش ثبت می‌شوند و فایل‌های موقت پس از اجرا پاک می‌شوند.

## پیکربندی برنامهٔ جدید

از [config.json](../examples/execution/config.json) شروع کنید. مسیرهای نسبی `source_dir` و `input.path` نسبت به فایل JSON هستند.

| فیلد | کاربرد |
| --- | --- |
| `target_id` | شناسهٔ برنامهٔ هدف |
| `versions.base` و `versions.patched` | پوشه‌های سورس و در صورت وجود `commit_hash` کامل همان نسخه |
| `build.binary` | مسیر نسبی فایل اجرایی داخل کپی سورس |
| `build.commands` | آرایهٔ دستورهای ساخت. هر دستور آرایه‌ای از آرگومان‌هاست |
| `build.clean_commands` | آرایهٔ اختیاری دستورهای پاک‌سازی کش و تنظیمات بیلد، مثل `[["make", "clean"]]`؛ قبل از دستورهای ساخت و در کپی همان بیلد اجرا می‌شود |
| `build.translation_units` | فهرست اختیاری مسیرهای نسبی فایل‌های C/C++ تشکیل‌دهندهٔ هدف؛ بدون این فیلد تمام سورس‌های شناخته‌شده در کپی باید شواهد کامپایل داشته باشند |
| `limits.build_timeout` | سقف زمانی مجموع دستورهای ساخت هر نسخه و بیلد، پیش‌فرض ۱۲۰ ثانیه |
| `limits.timeout` | سقف زمانی هر اجرا، پیش‌فرض ۵ ثانیه |
| `limits.max_output_bytes` | سقف جداگانهٔ هر جریان خروجی، پیش‌فرض ۱ MiB |
| `tests[].id` | شناسهٔ یکتای تست |
| `tests[].category` | یکی از `valid`، `boundary` و `invalid` |
| `tests[].input.mode` | یکی از `argv`، `stdin` و `file` |
| `tests[].args` | آرگومان‌های برنامه. برای حالت فایل دقیقاً یک آرگومان مستقل `{input}` |
| `tests[].expected` | کد خروج، stdout و در صورت نیاز stderr مورد انتظار. مقایسهٔ متن دقیق است و newline هم حساب می‌شود |
| `tests[].reference` | شناسه یا پیوند مستندات رفتار مورد انتظار |

در دستور ساخت، آرگومان مستقل `{flags}` به پرچم‌های همان بیلد و `{binary}` به مسیر فایل اجرایی تبدیل می‌شود. برای سیستم‌های ساخت مثل Make، این پرچم‌ها در `CFLAGS`، `CXXFLAGS` و `LDFLAGS` هم در دسترس‌اند. دستورها در کپی تمیز سورس اجرا می‌شوند و دستور ساخت باید پرچم‌های لازم را در کامپایل و لینک به کار ببرد. برای بیلد sanitized از لینک مستقیم با کامپایلر یا فرمان ساختی استفاده کنید که تنظیمات sanitizer را به لینک نهایی منتقل کند.

پیش از هر بیلد، فایل‌های کامپایل‌شدهٔ کپی سورس حذف می‌شوند: objectها، آرشیوها، کتابخانه‌ها، precompiled headerها و LLVM bitcodeهای شناخته‌شده. فایل‌های ELF و آرشیو حتی با نام غیرمعمول از روی محتوای فایل شناسایی می‌شوند. فهرست حذف‌ها در `builds[].removed_build_artifacts` ثبت می‌شود؛ سورس اصلی و خروجی‌های قبلی آن تغییر نمی‌کنند. لینک نمادین به خارج از کپی سورس پذیرفته نمی‌شود، تا فایل‌های کامپایل‌شدهٔ بیرون از کپی دوباره مصرف نشوند.

برای کش‌ها و تنظیمات اختصاصی Make/CMake یا سیستم ساخت دیگر، `build.clean_commands` را تعریف کنید و configure را در `build.commands` دوباره اجرا کنید. پاک‌سازی خودکار پیش از این دستورها انجام می‌شود؛ دستور پاک‌سازی باید نبودن objectها و باینری‌های قبلی را تحمل کند. دستورهای پاک‌سازی و ساخت یک سقف زمانی مشترک دارند و فیلد `commands[].phase` مشخص می‌کند هر دستور از کدام مرحله است. شکست پاک‌سازی باعث توقف همان بیلد و ثبت اجراهای انجام‌نشده می‌شود.

کتابخانهٔ ازپیش‌ساخته‌شدهٔ لازم برای هدف باید از سورس بازسازی شود؛ در غیر این صورت ساخت ممکن است شکست بخورد. بررسی `readelf` فقط وجود runtimeها را تأیید می‌کند. برای بیلد Sanitized علاوه بر آن، فرمان واقعی کامپایل هر واحد C/C++ نیز بررسی می‌شود.

در بیلد Sanitized، متغیرهای `CC` و `CXX` و نام‌های معمول کامپایلر در `PATH` به واسط کنترل‌شده اشاره می‌کنند. این واسط پرچم‌های Sanitizer را به هر فراخوانی اضافه می‌کند؛ بنابراین حتی دستور `gcc -O2 -c helper.c` که `CFLAGS` را نادیده گرفته، با تنظیمات لازم اجرا می‌شود. فرمان مؤثر، نتیجهٔ کامپایل، مسیر و SHA-256 سورس در `builds[].compiler_audit` ثبت می‌شوند. ساخت موازی Make نیز پشتیبانی می‌شود. گزینه‌هایی که Sanitizer را غیرفعال یا به trap تبدیل می‌کنند و آرگومان‌های پنهان‌شده در response file مثل `@args.rsp` فعلاً پذیرفته نمی‌شوند؛ برای response file آرگومان‌ها را در دستور ساخت باز کنید.

اگر یک Makefile از مسیر مطلق کامپایلر استفاده کند و این واسط را دور بزند، برای فایل مربوط شواهد کامپایل ثبت نمی‌شود. در این وضعیت بیلد Sanitized با `compiler_audit.status=unverified` رد می‌شود، اجراهای وابسته انجام نمی‌شوند و CLI کد ۳۰ می‌دهد؛ وجود runtime در باینری باعث پذیرش آن نخواهد شد. از `$(CC)` و `$(CXX)` استفاده کنید یا متغیرهای Make را با دستورهایی مانند `["make", "CC=gcc", "CXX=g++"]` تنظیم کنید. مسیر مطلق کامپایلرهای شناخته‌شده در خود `build.commands` به واسط نگاشت می‌شود، اما مسیرهایی که داخل اسکریپت یا Makefile نوشته شده‌اند قابل بازنویسی خودکار نیستند.

برای پروژه‌ای که سورس‌های آزمایش یا ابزارهای غیرمرتبط هم دارد، `build.translation_units` را با همهٔ واحدهای واقعی هدف، از جمله فایل‌های کمکی و سورس کتابخانه‌های خود پروژه، تنظیم کنید؛ نمونه: `["main.c", "src/parser.c"]`. سورس تولیدشده نیز باید در این فهرست بیاید. وضعیت `verified` فقط به فایل‌های فهرست‌شده و هش ثبت‌شدهٔ آن‌ها مربوط است و در گزارش با `scope` مشخص می‌شود. این بررسی برای صحت تنظیمات ساخت است؛ اثبات ابزارگذاری تک‌تک دستورها، رفتار build script خصمانه، کتابخانه‌های سیستمی یا annotationهای سورس مانند `no_sanitize` نیست. صحت فهرست واحدهای هدف باید هنگام آماده‌سازی برنامه‌های اصلی بازبینی شود.

ورودی stdin و فایل از `text` با UTF-8 یا `path` به‌شکل بایت خوانده می‌شود. مسیر فایل فقط یک بار خوانده می‌شود تا تغییر آن در میانهٔ اجرا روی مقایسهٔ دو نسخه اثر نگذارد. در حالت فایل، `name` اختیاری است و برای برنامه‌ای که به پسوند حساس است کاربرد دارد. فایل ورودی در دایرکتوری تازهٔ همان اجرا ساخته می‌شود.

برای هدف‌های اصلی، مقدار `expected` را از مستندات برنامه یا آزمون مرجع مستقل و مورد تأیید مدرس بگیرید. مقدار `commit_hash` در گزارش از پیکربندی منتقل می‌شود. ابزار هش SHA-256 باینری ساخته‌شده را خودش محاسبه می‌کند.

## Square fixture oracle

طبق مشخصات نمونه، عدد صحیح بین صفر و صد پذیرفته و مربع آن با newline روی stdout نوشته می‌شود. ورودی خارج از این بازه یا ورودی غیرعددی کد ۲ و پیام `invalid number` در stderr دارد.

| شناسه | دسته | کانال و مقدار | exit | stdout |
| --- | --- | --- | --- | --- |
| `argv-valid` | معتبر | آرگومان `7` | ۰ | `49\n` |
| `file-lower-bound` | مرزی | فایل شامل `0\n` | ۰ | `0\n` |
| `stdin-upper-bound` | مرزی | stdin شامل `100\n` | ۰ | `10000\n` |
| `argv-invalid` | نامعتبر | آرگومان `abc` | ۲ | رشتهٔ خالی |
| `stdin-out-of-range` | نامعتبر | stdin شامل `101\n` | ۲ | رشتهٔ خالی |

دو نسخهٔ این fixture برای بررسی قرارداد اجرا استفاده می‌شوند. انتخاب برنامه‌های اصلی و تأیید آزمون‌های مرجع در تحویل گروهی انجام می‌شود.

## نتیجهٔ اجرا و ادغام

ترتیب ماتریس `build_type × test × version` است. هر بیلد برای نسخهٔ پایه و وصله‌شده جداگانه ساخته می‌شود. `release` با `-O2 -DNDEBUG` و `asan_ubsan` با ASan و UBSan، نمادهای دیباگ و frame pointer ساخته می‌شود. گزارش شواهد وجود یا نبود runtimeهای sanitizer در ELF را در `builds[].instrumentation` نگه می‌دارد.

| بخش | داده |
| --- | --- |
| `builds[]` | نسخه، حالت ساخت، دستورها، لاگ ساخت، ریشهٔ سورس، وضعیت، فایل اجرایی و SHA-256 |
| `builds[].compiler_audit` | برای Sanitized: محدودهٔ بررسی، وضعیت شواهد هر فایل، هش سورس و فراخوانی‌های واقعی کامپایلر |
| `tests[]` | شناسه، دسته، انتظار مرجع، روش ارسال ورودی و هش دادهٔ ورودی در حالت فایل یا stdin |
| `executions[]` | یک مشاهده برای هر ترکیب. شامل `test_id`، `version`، `build_type`، `commit_hash`، `exit_code`، `signal`، `timeout`، `stdout` و `stderr` |
| `executions[].findings` | نوع و روش تشخیص همراه با شواهد اصلی. فریم‌های sanitizer با parser نفر اول به دست می‌آیند |
| `executions[].expectation` | `pass`، `fail`، `runtime_error` یا `inconclusive` به‌همراه فیلدهای ناهماهنگ |
| `skipped[]` | اجراهایی که به علت شکست ساخت انجام نشده‌اند |

`exit_code` برای خروج عادی ثبت می‌شود. در خاتمه با سیگنال، مقدار آن `null` است و نام و شمارهٔ سیگنال جدا ثبت می‌شوند. Timeout و عبور از سقف خروجی در `runner_stop` ثبت می‌شوند. وقتی اجرای runner جریان بازی را قطع می‌کند یا سقف خروجی پر می‌شود، پرچم‌های truncation احتمال ناقص بودن خروجی را نشان می‌دهند. خروجی غیر UTF-8 در فیلد `*_base64` هم ثبت می‌شود.

مثلاً `SIGSEGV` شواهد segmentation fault است. گزارشی از ASan با عنوان `heap-buffer-overflow` شواهد دقیق‌تری دارد و ممکن است فریم سورس هم داشته باشد. پیام stack smashing همراه با `SIGABRT` شواهد مربوط به stack protector است. خطاهای راه‌اندازی ASan از طریق `launch_error` گزارش می‌شوند. کد خروج غیرصفرِ مطابق انتظار، مانند ۲ برای ورودی نامعتبر نمونه، آزمون موفق محسوب می‌شود.

عبارت عمومی `runtime error: ...` و پیشوند شماره‌دار مانند `validator:42:` به‌تنهایی، حتی در بیلد Sanitized، گزارش UBSan محسوب نمی‌شوند. در فرم بدون نام صریح Sanitizer، نام فایل C/C++ و متن تشخیصی شناخته‌شده باید با هم وجود داشته باشند؛ گزارش ناشناخته با فریم native بلافاصله بعد از آن نیز حفظ می‌شود. سربرگ صریح `ERROR/SUMMARY: UndefinedBehaviorSanitizer: ...` همچنان پشتیبانی می‌شود. پیام `validator.c:42: runtime error: input invalid` نیز finding نمی‌سازد. این قواعد برای stdout و stderr یکسان‌اند؛ تفسیر متن لاگ به‌تنهایی اثبات اصالت گزارش نیست.

برای ادغام پایتونی، `load_config(path)` و `run_suite(config)` از `security_patch_validator.execution` قابل فراخوانی‌اند. هر عضو `executions[]` مستقیماً ورودی `parse_execution_result` است. ماژول ادغام می‌تواند با `test_id` و `build_type` مشاهده‌های متناظر را گروه‌بندی کند و پس از تکرارهای لازم، آن‌ها را در `tests[].executions` [قرارداد classifier](classifier-contract.md) بگذارد. برای تطبیق مسیرهای مطلق فریم‌ها با diff می‌توان `source_root` همان بیلد را به `--source-root` داد.

کد خروج `execute` وضعیت جمع‌آوری شواهد را مشخص می‌کند.

| کد | وضعیت |
| --- | --- |
| ۰ | اجرای ماتریس تکمیل شده و نتیجهٔ هر تست در گزارش موجود است |
| ۳۰ | خطای ساخت، پیکربندی، محیط یا راه‌اندازی فرایند |
| ۴۰ | جمع‌آوری ناقص به دلیل Timeout یا محدودیت منابع |

کد خروج نهایی ارزیابی وصله را `classify` تعیین می‌کند.

## Native regression tests

فایل `tests/integration/test_execution_regressions.py` برنامه‌های کوچک C و C++ را در پوشهٔ موقت می‌سازد و از API واقعی `load_config → run_suite` استفاده می‌کند. انتظارهای مرجع در خود تست‌ها مشخص‌اند:

| سناریو | نتیجهٔ مورد انتظار |
| --- | --- |
| ورودی معتبر و دسترسی به آخرین بایت مجاز | موفقیت در هر دو نسخه و هر دو بیلد |
| ورودی نامعتبر با پیام عمومی `runtime error: input invalid` | خروج ۲ و موفقیت آزمون، بدون finding جعلی |
| دسترسی یک بایت پس از انتهای heap | `asan / heap-buffer-overflow` در Base Sanitized؛ موفقیت نسخهٔ اصلاح‌شده |
| خواندن حافظه پس از free | `asan / heap-use-after-free` در Base Sanitized؛ موفقیت نسخهٔ اصلاح‌شده |
| `INT_MAX + 1` | `ubsan / signed-integer-overflow` در Base Sanitized؛ خروجی `2147483648` با محاسبهٔ صحیح در نسخهٔ اصلاح‌شده |
| حلقهٔ بی‌نهایت در C | Timeout، حفظ لاگ و ثبت SIGKILL بدون نسبت‌دادن آن به خطای خود برنامه |
| object و آرشیو ساخته‌شده با Release در پوشهٔ سورس | حذف در کپی بیلد، بازسازی با sanitizer و تشخیص سرریز |
| Makefile که `CFLAGS` را برای helper نادیده می‌گیرد | اعمال پرچم‌ها توسط واسط کامپایلر و تشخیص سرریز واقعی |
| کامپایل helper با مسیر مطلق خارج از واسط | رد بیلد Sanitized به‌علت نبودن شواهد همان فایل |
| لاگ شماره‌دار برنامه با پیام `input invalid` | موفقیت آزمون بدون finding جعلی در هر دو بیلد |
| خطای دستور پاک‌سازی | حفظ stderr و کد خروج، شکست بیلد و انجام‌نشدن اجراهای وابسته |

برای خطاهای دارای رفتار تعریف‌نشده، سالم‌ماندن یا خراب‌شدن Release قابل اتکا نیست؛ تست تشخیص خطا روی Base Sanitized و رفتار صحیح روی نسخهٔ اصلاح‌شده بررسی می‌شود. این نمونه‌ها برای اعتبارسنجی ابزارند و جای دو برنامهٔ اصلی مورد تأیید مدرس را نمی‌گیرند.

~~~bash
# تست‌های نفر دوم؛ بدون نیاز به pytest (GCC/G++، binutils و Make لازم‌اند)
PYTHONPATH=src python3 -m unittest discover -s tests/integration -v

# کل مخزن در محیط توسعه‌ای که pytest نصب دارد
PYTHONPATH=src python3 -m pytest
~~~

فایل‌های لاگ مرجع parser در `tests/fixtures/` همراه کد نگهداری می‌شوند و نباید به‌دلیل قاعدهٔ عمومی نادیده‌گرفتن فایل‌های `.log` از Git حذف شوند.

## تمرین دفاع فردی

- در `argv-invalid` کد ۲ را با انتظار مرجع مقایسه کنید و توضیح دهید چرا آزمون موفق است.
- برای `stdin-upper-bound` خروجی دو نسخه را در هر دو بیلد بررسی کنید.
- در آزمون Timeout، تفاوت `signal` و `runner_stop` را توضیح دهید.
- مقدار `expected.stdout` مربوط به `argv-valid` را به `50\n` تغییر دهید و تفاوت `expectation.status` را در گزارش بررسی کنید.
